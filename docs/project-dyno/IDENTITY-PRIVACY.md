# Identity and privacy

Wallet login signs a short-lived message containing domain, URI, chain ID, nonce, issued-at and expiry. Nonces are random and consumed. Discord uses authorization-code OAuth, state, `identify` and `guilds.members.read`. OAuth access/refresh tokens are not retained. Owner-selected production storage is a private SQLite file on `/var/data`, with AES-256-GCM-encrypted sessions, challenges, identity observations and audit payloads. Cookie/state identifiers are stored only as keyed digests; AAD binds ciphertext to its namespace/identifier. Public events and checkpoint hashes are unencrypted index data. This does not claim whole-database encryption or horizontal scaling.

`HMAC-SHA256(identity-secret, "discord:v1:" + user-id)` creates the stable commitment. Back up the secret separately. Rotation is a migration: derive v2, propose relinks, retain the old/new map and increment versions. Replacing the key without migration is prohibited.

The relink contract requires an administrator transaction **and** an unexpired EIP-712 `RelinkAuthorization` signed by the proposed new wallet (EOA or supported ERC-1271 wallet). The signature binds the stable commitment, new wallet, expected identity version, chain and proxy; changing the version prevents replay. The draft-only admin view can copy the new-wallet signing request, accept its signature and ask the server to simulate and prepare exact calldata. It never signs for the new wallet or executes the multisig transaction. This flow still needs real-wallet/contract-wallet acceptance and operator review before release; an observed OAuth wallet is not approval or a relink. Existing claims stay with the original wallet. Account/day counts survive relink and old wallet/day history remains. Suspension blocks vouchers only.

Public exports use commitments. Admin exports may include ID/name/link history and authorized evidence references. Formula-like CSV cells receive an apostrophe. Tokens, sessions, secrets and private evidence are never exported.

Private identity reads: `/api/dyno/admin/identities` and `.csv` expose paginated current observations; `/api/dyno/admin/identity-history?commitment=…` exposes up to 250 decrypted audit observations for exactly one commitment, with a corresponding HISTORY action in the admin table. All require a valid wallet session and a fresh on-chain Safe-owner or configured emergency-admin check, are non-cacheable and return the authority block. They do not include review evidence or constitute on-chain relink approval. The public ledger endpoints never join this mapping. These routes remain disabled with the production raffle until a reviewed release.

## Checkout readiness (local implementation, 2026-10-12)

Authenticated `/api/dyno/quota` reads the active round, phase, pause, suspension, both platform-wide daily counters, wallet/account binding, identity version and accepted signer from the same numbered chain block. It returns the block hash, timestamp, exact remaining allowance and next UTC reset. Blocks more than 120 seconds old, more than 30 seconds in the future, on another chain, from yesterday at UTC midnight, or changed during the read are rejected. RPC failures expose no endpoint credentials.

Voucher issuance repeats those reads, rejects batches larger than quota/capacity, derives the identity version from chain (never from a browser parameter), and requires the configured signing key to match the on-chain signer. Signing across a UTC midnight boundary is rejected. A quota response is advisory, not a reserved ticket or allowance: concurrently issued vouchers remain subject to the contract's atomic quota/capacity checks.

The browser restores a still-valid wallet login after the OAuth redirect, shows chain-read quota, leaves checkout disabled when verification/state is unavailable, and obtains fresh quote/voucher data after any separate approval transaction. Expired wallet sessions cannot access quota, vouchers or admin preparation. Malformed signatures and malformed cookie encoding fail safely. SQLite authentication is durable across restarts; `take` consumes a challenge/state in one immediate transaction across local connections. Memory storage remains explicitly local/demo only.

Identity observations are recorded only after wallet+Discord authentication and successful chain-read eligibility checks. A pending first binding is marked `bindingConfirmed=false`; confirmed bindings/versions come from the chain. These observations never approve a relink, change quota, create tickets or confer administrative power. The secret-key fingerprint and stable Discord digest reject accidental commitment/key replacement. The encrypted audit records observed wallet/version changes, not proof of unique personhood.

Local authentication throttles now bound nonce and signature attempts by client bucket and wallet, and quota/voucher reads by client bucket and authenticated wallet. SQLite stores keyed digests, not raw IPs, and fixed-window counters survive process restarts. A 429 response is a temporary service throttle, not a cheating finding, ticket-count adjustment or suspension. Shared networks can be rate-limited; tune and monitor limits before production release. This does not replace edge-level abuse controls or a review of trusted proxy headers.
